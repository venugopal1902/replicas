Churn Buster

Failed-payment recovery that cancels the dunning the moment they pay. No $269/mo floor.

Replaces Churn Buster Version 0.1.0 License MIT Runtime Python 3.12

Overview#

Churn Buster sells failed-payment recovery and cancellation flows starting at $269 a month, scaling with MRR. This engine reproduces the recovery loop: Stripe-shaped webhook intake, dunning campaigns with ordered steps and delays, duplicate suppression, recovery that cancels every pending email, recovery analytics with MRR at risk and recovered MRR, an admin console and a CSV report. Emails are recorded as dry_run unless SMTP is configured, and webhook signature verification activates as soon as STRIPE_WEBHOOK_SECRET is set.

replaces Churn Busterv0.1.0MITPython 3.12

What you get

  • 21/21 checks passing against a live server
  • Stripe-shaped webhook with optional HMAC signature check
  • Three-step dunning campaign with delays
  • Recovery cancels pending sends
  • Duplicate failures do not re-enrol a customer
  • Recovery rate, MRR at risk, recovered MRR
  • Dry-run by default, never fakes a delivery

Failure intake

invoice.payment_failed and charge.failed open a failure and enrol the customer. A simulator does the same without Stripe.

Campaigns

Ordered steps with per-step delays. The seeded campaign fires at 0, 1 day and 3 days.

Recovery

invoice.paid or a manual mark flips the failure to recovered and cancels every queued email for it.

Analytics

Failure counts, recovery rate, MRR at risk and recovered MRR, computed from the tables not estimated.

Honest sends

SEND_MODE=dry_run records dispatch without transmitting. Nothing is labelled sent unless SMTP was used.

Admin console at / on port 8610.

Install#

From a clean machine to a running server in four commands.

Requirements

  • Python 3.11 or newer
  • uv (Astral)
  • No Stripe account needed for the simulator or the test suite

Step 1 · Clone

Get the source.

git clone https://github.com/venugopal1902/replicas.git
cd replicas/services/churn-buster

Step 2 · Install

Create the environment.

uv sync

Step 3 · Run

Admin console on port 8610.

uv run python scripts/run_server.py

Run the suite with the server up

cd services/churn-buster
uv run python tests/test_churn_buster.py

Usage#

Open a failure without Stripe

Creates the customer if needed, opens a failure and queues one email per campaign step.

TOKEN=$(curl -s -X POST http://127.0.0.1:8610/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@churnbuster.local","password":"churnbuster123"}' | jq -r .token)

curl -s -X POST http://127.0.0.1:8610/api/simulate/payment-failure \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"customer_email":"maya@example.com","amount_cents":4900,"mrr_cents":4900}'

Recover with a Stripe-shaped webhook

Payment lands, the failure closes and every pending dunning email is cancelled.

curl -s -X POST http://127.0.0.1:8610/webhooks/stripe \
  -H 'Content-Type: application/json' \
  -d '{"type":"invoice.paid","data":{"object":{"customer_email":"maya@example.com","amount":4900}}}'

Operational notes#

Read before going live. These are the things that break in production.
  • SEND_MODE defaults to dry_run. Dispatch records emails, it does not transmit them.
  • STRIPE_WEBHOOK_SECRET unset means webhooks are accepted and labelled stripe-sim. Set it in production.
  • This engine orchestrates communication and reporting. Charge retries belong to Stripe.
  • Cancellation flows, A/B tests and segmentation are not implemented yet.

FAQ#

Does it retry the card charge?

No. Stripe owns retry logic. This engine handles the customer communication and the recovery analytics around it.

Will a real Stripe webhook work?

Yes once STRIPE_WEBHOOK_SECRET is set. The endpoint accepts the Stripe event shape and verifies the stripe-signature HMAC.
