Smile Engine

An append-only points ledger with derived balances. Spending cannot corrupt the history.

Replaces Smile.io Version 0.1.0 License MIT Runtime Python 3.12

Overview#

Smile.io sells loyalty points, referrals and VIP tiers from $15 to $199 a month. This engine treats the program as what it actually is: a ledger. There is no mutable balance column. Balance is always SUM(points) over append-only entries, every mutation carries an idempotency key, a refused redemption writes nothing, referrals award both sides while refusing self-referral and duplicate referees, and tiers derive from lifetime earned points so spending never demotes a member.

replaces Smile.iov0.1.0MITPython 3.12

What you get

  • 22/22 checks passing on the first run
  • No mutable balance column: balance is derived from entries
  • Idempotency key required on every earn and redeem
  • A refused redemption writes no ledger entry
  • Self-referral and duplicate referees refused
  • Tiers from lifetime earned, not spendable balance
  • Full ledger CSV export

Ledger

Append-only earn, redeem and adjust entries, each with a reason, timestamp and unique idempotency key.

Idempotency

Replaying a request cannot double-award or double-spend. The endpoint reports duplicate rather than failing.

Redemption

A short balance returns 409 and writes nothing, so the ledger never records a spend that did not happen.

Referrals

Referrer and referee both earn. Self-referral and referring an existing member are refused.

Tiers

Bronze/silver/gold/platinum from lifetime earned, with progress to the next tier.

Interface#

Console at / on port 8660 listing members with derived balances and tier progress.

Install#

From a clean machine to a running server in four commands.

Requirements

  • Python 3.11 or newer
  • uv (Astral)
  • ADMIN_PASSWORD set before first start

Step 1 · Clone

Get the source.

git clone https://github.com/venugopal1902/replicas.git
cd replicas/services/smile-engine

Step 2 · Install

Create the environment.

uv sync

Step 3 · Set the admin password

Required on first start.

export ADMIN_PASSWORD='choose-a-long-unique-password'

Step 4 · Run

Console on port 8660.

uv run python scripts/run_server.py

Run the suite with the server up

cd services/smile-engine
uv run python tests/test_smile.py

Usage#

Earn and spend safely

Both calls take an idempotency key, so a network retry is harmless. Balance is recomputed from the ledger on every read.

curl -s -X POST http://127.0.0.1:8660/api/members/$MEMBER/earn \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"points":300,"reason":"purchase","idempotency_key":"order-1041"}'

curl -s -X POST http://127.0.0.1:8660/api/members/$MEMBER/redeem \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"reward_id":"rw_latte","idempotency_key":"redeem-1041"}'

# a short balance returns 409 and writes nothing

Operational notes#

Read before going live. These are the things that break in production.
  • No Shopify integration: members are created through the API.
  • No points expiry, so outstanding liability grows. That is the next thing to build for production.
  • Refunds should be negative adjust entries; the schema supports it, no endpoint exposes it yet.
  • No fraud scoring beyond self-referral and duplicate-referee refusals.

FAQ#

Why is there no balance column?

Because balances drift out of sync with history. Deriving the balance from append-only entries makes that impossible by construction.

What happens if a redemption request is retried?

The idempotency key makes the second call a no-op that reports duplicate, so points are spent once.
